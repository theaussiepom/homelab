# Root Zabbix monitoring

The site-root `zabbix` field enables monitoring. It is separate from references that pass values between apps.

| Source | Meaning |
| --- | --- |
| Property absent | No root monitoring expansion |
| zabbix: null (or empty YAML value) | Exactly one selected Zabbix app must exist; select it |
| zabbix: {server: app_id} | Select that existing Zabbix app |
| false, true, empty object, extra keys | Refused |

Your site must still declare the Zabbix app, its guest, database and metrics connections, software and exposure. Adding the root field does not allocate a guest. Every selected guest's combined monitoring profiles must include linux.

Ordinary app preparation currently requires the database credential generated by root monitoring and its exact monitoring files. A Zabbix app configured without the root feature may pass configuration checks with a selected `database_password`, but ordinary preparation does not support that combination. Successful source checks therefore do not provide a standalone server installation procedure. Supplying an arbitrary scalar password cannot replace the credential managed by root monitoring.

## Derived behavior

The compiler generates active Agent2 settings and stable host and pre-shared key (PSK) identities based on node and VMID. Profiles select Linux, Docker, PostgreSQL, MySQL or InfluxDB support. Docker monitoring gives the local agent access to the guest's Docker group and API; it does not publish a central Docker socket.

Root monitoring adds specific traffic rules: active TCP port 10051 between monitored guests and the server, frontend TCP port 8080 from the selected ingress, and the selected PostgreSQL and InfluxDB storage connections. Ordinary connections and value references do not otherwise grant access. Database statistics accounts and monitoring credentials follow their own create-once ownership rules.

The monitoring server cannot be disabled while other guests remain enabled. You can compile an inventory with every guest disabled for inspection. Checks of the server's managed inventory, templates, PSKs, SAML and database readiness remain separate from tests of the actual running service.

See [authentication policies](policies.md#authentication-policies) and [app properties](app-properties.md#authentik-and-zabbix). Adding the root field does not establish support for first-time commissioning or automatic restore, or guarantee TLS identity checks. Support depends on the selected library profile, prepared private inputs and target prerequisites.

## Credentials, login and preservation

The controller creates monitoring credentials once and stores them privately with their ownership records. Do not print, regenerate or replace an established PSK or password to repair a failed run. Template and inventory updates preserve host identities, secret macros and history; they do not use destructive deleteMissing imports.

Selecting SAML as the default login method changes the entry screen. It does not change password or API authentication, or user roles. The vendor local recovery form remains at `/index.php?form=default`. Keep a working local administrator and verify the real SSO session separately. The public IdP certificate is not a private key.

PostgreSQL storage managed by monitoring requires the existing native TLS precheck and exact HBA rules. It does not create or replace production database certificates. Establishing an encrypted connection alone does not prove certificate identity checks. Discovering InfluxDB organizations and buckets requires a separately scoped credential; a metrics connection does not supply it.

## Worked selection and profile

This is a **site-root fragment**, not an installation recipe:

<!-- example: zabbix-selection -->
```yaml
zabbix: {server: monitoring}
```

It selects an already declared Zabbix app named `monitoring`. A reusable `monitoring_profiles.linux_host` value can be:

<!-- example: zabbix-profile -->
```yaml
type: zabbix-agent
profiles: [linux]
```

A template or guest can then select `monitoring: {profile: linux_host}`. Add `docker` to the same profile only for a guest whose selected workload needs that integration and whose runtime prerequisites are supported. Root monitoring still requires the declared server's database, software and connections. **Invalid variation:** `zabbix: false` is rejected; omit the field to disable the feature. `profiles: [docker]` validates as a profile type but does not satisfy the root feature's required Linux profile for every selected guest. A later run updates the owned monitoring configuration without replacing host identities or regenerating existing credentials.
